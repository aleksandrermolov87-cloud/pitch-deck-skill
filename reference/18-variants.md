# Варианты компонентов по смыслу и форме данных

Последовательный подбор «вопрос → строка каталога» часто приводит к одним и тем же привычным раскладкам. `scripts/variants.py`
предлагает на каждый слайд 2–3 пригодных компонента: по смыслу слайда и по форме данных, которые есть в брифе. Для каждого
кандидата видно, какие поля есть, каких нет и что компонент сделает без них, какие у него лимиты и как он выглядит.
Неподходящие компоненты не прячутся: у каждого записана причина исключения. Режим показа собирает варианты на том же
содержании в обеих темах, пользователь выбирает вариант по слайду, выбор записывается.

Главное правило то же, что в факт-чеке: **выдуманных полей нет**. Если в брифе нет настроения клиента, `journeyMap` получает
статус «частично: нет stages[].mood» или исключается, но не предлагается как заполненный. Если пять строк рейтинга не
составляют целое, `treemap` и `stackedShare` исключены: «Прочие» до 100% были бы выдумкой.

## Когда запускать

- **Этап 0, скелет.** Если слайду подходят несколько компонентов, а `slides.js` ещё нет: опиши содержание слайдов в файле
  формы (ниже) и запусти `suggest --content`. В скелет-таблицу идёт выбранный компонент, в план — строка «варианты: A, B, C».
- **Этап 2 и после сборки.** `suggest` без `--content` снимает содержание прямо со `slides.js`: вызывает функции слайдов
  с перехватом `K.*`, PPTX не собирает. Так видно, чем ещё можно показать уже собранный слайд.
- **Слайд вернулся с этапа 5** (2+ сигнала банальности): `suggest --slides N`, затем `demo`.
- **Обновление навыка.** `suggest --lib skill` проверяет и показывает кандидатов на библиотеке навыка, а не деки: что даст
  обновление на том же содержании (тема и подложки остаются деки).

## Команды

```bash
PY="$SKILL/.venv/bin/python -I"
$PY $SKILL/scripts/variants.py suggest src-<тема> [--slides 4,6,9] [--content форма.json] [--lib skill] [--top 3]
$PY $SKILL/scripts/variants.py demo    src-<тема> [--run <id>] [--slides 4,9] [--all]
$PY $SKILL/scripts/variants.py pick    src-<тема> --slide 9 --variant B [--run <id>] [--why "рейтинг читается лучше"]
$PY $SKILL/scripts/variants.py check
```

- `suggest` создаёт прогон `out/variants/<id>/`: `suggest.json` (замороженное содержание и кандидаты с готовыми данными)
  и `suggest.md` (таблица для чтения). В сообщение пользователю идут таблицы слайдов, где вариантов 2+.
- `demo` собирает по слайду на вариант в черновом проекте `out/variants/<id>/src` (та же библиотека, тема и подложки, что
  у деки; `build.js` и `render.sh` без изменений) и складывает листы `sheet-s<N>.png`: строка — вариант, слева тёмная тема,
  справа светлая, над строкой статус и переполнения. Рядом `Варианты.pptx` и `Варианты_светлая.pptx` и `demo.json`
  (переполнения и ошибки по вариантам). Без `--slides` показываются слайды, где вариантов два и больше.
- Повторный `demo` по прогону, который уже показан, пишет новый прогон с тем же замороженным содержанием (`repeat_of`
  в `suggest.json`): прошлые листы и PPTX не меняются, правки `slides.js` между запусками на показ не влияют.
- `pick` пишет выбор в `data/variants.json` и готовый вызов `K.<компонент>(body, data, opt)` в `out/variants/<id>/pick-s<N>.js`.
  В `data/variants.json` только ссылки (компонент, буква, прогон, хэши содержания и данных, итог показа, причина), без
  текстов слайда: `copy_edit.py` ищет формулировки в `data/*.json`, копия текста сделала бы правки неоднозначными.
  Следующий `suggest` отмечает прошлый выбор и пишет, если содержание слайда с тех пор изменилось.
- `check` сверяет `components/fields.json` с библиотекой (у каждого компонента есть запись), переложения с `accepts`
  и образцы галерей с обязательными полями. Код 1 при расхождении — запускать после добавления компонента.

Слайд в деку агент переносит сам: заменяет вызов компонента в `slides.js` на `pick-s<N>.js` (бокс и `opt.show` — свои),
затем `ONLY=<n> node build.js && SLIDE='<n>' ./render.sh`, `library_check.py`, `facts_check.py`.

## Как выбираются кандидаты

1. **Форма данных.** Содержание слайда приводится к одной из форм (таблица ниже). Со `slides.js` форму даёт текущий
   компонент: `comparison` → `matrix`, `processSteps` → `steps`, таблица из имени и одного числового столбца → `ranked`.
   На слайде с несколькими компонентами варианты подбираются для главного (наибольший бокс), остальные не меняются.
2. **Переложение.** Для каждого компонента, который принимает эту форму (`accepts` в `fields.json`), данные перекладываются
   без досочинения: поля переименовываются, `true/false` в таблице становятся «да/нет». Чего нет — того нет. Смысловые
   проверки исключают компонент с причиной: части не составляют целое, у метрик разные единицы, значения не уровни 0–3,
   нет дат, экранов, критериев перехода, центра схемы; крупное сравнение показывает одну метрику и не прячет остальные.
3. **Сверка с каталогом.** Данные компонента сверяются с `components/fields.json`: нет обязательного поля — исключён;
   число элементов вне рассчитанного диапазона — исключён (у текущего компонента — предупреждение); нет необязательного
   поля с пометкой — «не заполнено» с объяснением; текст длиннее проверенного в галерее — предупреждение.
4. **Пробный вызов.** Каждый кандидат вызывается в библиотеке деки (или навыка, `--lib skill`) на настоящем боксе тела.
   Падение, `NaN` в координатах, `undefined` или `{n}` в тексте, нечисловое значение в реестре фактов — исключение
   с текстом ошибки. Так «частичные данные» проверяются кодом: старая версия `rankingList` без `prev` падает и исключается
   с подсказкой «нужна версия компонента с частичными данными», новая рисует «нет данных».
5. **Ранжирование.** Главный вопрос слайда среди тегов смысла компонента +3 (+1, если это и главный вопрос компонента),
   доля общих тегов до +2, текущий компонент +0,5; каждое пустое смысловое поле (`key`) −1, длинный текст −0,3.
   Берутся `--top` лучших, текущий остаётся в списке. Компонент без общих тегов помечается «запасной: другой смысл».
   Остальные пригодные перечислены строкой «ещё годятся».

Статусы: **годится** — все смысловые поля есть; **частично** — нет смыслового поля (`key`), компонент рисует без него,
и это видно на слайде; **исключён** — с причиной. «Не заполнено» у статуса «годится» — второстепенные поля (3D-объект шага,
число у пункта сводки).

Пример отображения: в таблице `suggest.md` у кандидата путь к PNG из галереи библиотеки (`components/.gallery`, собрать
`zsh $SKILL/scripts/gallery.sh`), в `demo` — сам слайд на содержании деки.

## Файл формы (`--content`)

```json
{"slides": [
  {"n": 4, "title": "…", "sub": "…", "source": "Источник: …", "shape": "matrix", "meaning": ["compare-options"],
   "content": {"options": [{"name": "…", "note": "…"}], "rows": [{"name": "…", "values": ["…", "…"]}]}}
]}
```

Держи файл вне `data/` (например, `plan/variants.json`): `copy_edit.py` правит тексты в `data/*.json`. Числа — с `src`
(в корне `content` или у элемента), как в `slides.js`: без источника компонент не соберётся. Образец с вымышленными данными:
`tests/variants/content.json`, приёмочный тест — `zsh $SKILL/tests/variants/run.sh`.

| Форма | Поля `content` | Кто принимает |
|-------|----------------|---------------|
| `matrix` | `options [{name, note?, recommended?, price?, cost?, time?, pros?, cons?}]`, `rows [{name, values}]`, `unit?`, `rowHead?`, `ask?` | comparison, tableEditorial, pricingTiers, featureDots, heatmap, decisionOptions |
| `steps` | `steps [{name, note?, date?, mood?, pain? {t, value?, unit?}, screen?, object?, due?, owner?, criteria?, gate?}]`, `current?` | processSteps, journeyMap, milestonesVertical, phaseGate, phoneFlow, nextStepsText, storyArc, executiveSummary, principles |
| `ranked` | `items [{name, value, prev?, us?, accent?, avg?, others?}]`, `label?`, `unit?`, `digits?`, `nameHead?`, `whole?` | rankingList, tableEditorial, usageRanking, nativeChart, treemap, stackedShare, kpiList, dotPlot |
| `series` | `periods`, `series [{name, values, main?}]`, `label?`, `unit?`, `digits?` | barsTrend, lineChart, kpiHero, pairedColumns, slope, dumbbell, nativeChart |
| `pair` | `from`, `to`, `metrics [{name, a, b, unit?, better?, digits?, caption_a?, caption_b?}]`, `notes? {a, b}`, `mode?`, `note?` | beforeAfter, bigCompare, dumbbell, slope, kpiGrid, tableEditorial |
| `kpis` | `items [{value, unit?, label, caption?, digits?, prev?, series?}]` | kpiList, kpiHero, executiveSummary, kpiGrid |
| `parts` | `parts [{name, value}]`, `label?`, `unit?`, `digits?`, `whole` (части составляют целое) | stackedShare, treemap, pictoGrid |
| `terms` | `items [{term, d, accent?}]` | glossary, principles |
| `qa` | `items [{q, a}]` | faqPairs |
| `points` | `items [{head, d, value?, unit?}]`, `lead?`, `accent?` | keyTakeaways, principles, executiveSummary, storyArc |
| `hub` | `center {name, note?}`, `nodes [{name, items, edge?}]` | hubDiagram, principles |
| `layers` | `groups [{name, note?, items [{name, note?}]}]`, `links?` | systemsLayers, nowNextLater, hubDiagram |

`whole` в `ranked` ставится, только если строки покрывают целое по источнику; иначе доли от суммы показанных строк
были бы новым, не названным в брифе числом.

Теги смысла (`meaning`): первый — главный вопрос слайда. По форме по умолчанию: `compare-options`, `process`, `ranking`,
`trend`, `change`, `kpis`, `share`, `definitions`, `faq`, `takeaways`, `roles`, `structure`. Остальные — в `fields.json`
у компонентов (`journey`, `pricing`, `headline-number`, `timeline`, `gates` и др.).

## Каталог `components/fields.json`

По записи на компонент: `group`, `question`, `archetype`, `data` (из `components/README.md`), `meaning` (теги смысла),
`accepts` (формы входа), `partial` (что компонент делает без смысловых полей), `fit` (`adaptive` — подбор размера под
содержимое), `fields` — поля данных:

- `type` — `text`, `number`, `bool`, `list`, `obj` или смесь (`bool|text`); у списка `of` — поля элемента (`item: "obj"`)
  или тип значений;
- `req` — без поля компонент не собирается: выведено пробным вызовом с удалённым полем на образце галереи и сверено вручную
  для частичных данных (`rankingList.rows[].prev`, `journeyMap.stages[].mood`, `pricingTiers.tiers[].price` — необязательные,
  `null` допустим);
- `key` — необязательное, но смысловое поле: без него статус «частично»; `about` — что значит поле и что будет без него;
- `tested` — сколько знаков (у списка — элементов) прошло в галерее в обеих темах без переполнений. Это проверенная длина,
  а не предел: длиннее — предупреждение, правду о переполнении даёт `demo`;
- `n` — рассчитанный диапазон числа элементов.

Новый компонент: строка в `README.md`, образец в `components/gallery-<группа>.js`, запись в `fields.json` (смысл, `accepts`,
поля по образцу), переложение в `variants.py` (`TO`, при необходимости `FROM`), затем `variants.py check`.

## Границы

- Содержание оценивается по полям и форме, а не по формулировкам: тексты проходят humanizer и SMART как обычно.
- Переполнение и посадка текста проверяются только в `demo` (рендер HTML-двойника); в PowerPoint варианты не открываются.
- Со `slides.js` снимаются только вызовы `K.*`: слайд из примитивов (`custom`) и обложка пропускаются с причиной.
- Числа, которые слайд регистрирует через `fact()` вне компонента, в варианты не переносятся.
