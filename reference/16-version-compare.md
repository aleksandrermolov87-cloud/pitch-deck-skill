# Контрольное сравнение версий навыка

Когда дека после обновления навыка выглядит иначе, причин может быть несколько: новая версия сборщика или компонентов,
изменённый бриф, другая разметка, другой шрифт, обновлённый Chrome. `scripts/version_compare.py` разделяет эти причины.
Он собирает одни и те же входы разными версиями в отдельных папках, фиксирует всё, что влияет на картинку, и сравнивает
слайды попиксельно.

## Когда запускать

- После `update.sh`: убедиться, что новая версия не сдвинула готовые деки (контрольное сравнение старой и новой версии на одних входах).
- Пользователь спрашивает «почему слайд стал другим?» или «что поменяла новая версия?».
- Перед релизом навыка, если менялись `build.js`, `lib.js`, `components.js`, `kit/` или `render.sh`: прогнать эталонную деку на прошлом и новом теге.
- Проверка воспроизводимости: две сборки одной версии на одних входах должны совпасть попиксельно.

## Порядок

1. **Прогон A** (было):
   ```bash
   $SKILL/.venv/bin/python -I $SKILL/scripts/version_compare.py run src-<тема> --runs version-runs --engine v1.5.0
   ```
2. **Прогон B** (стало): тот же проект с `--engine v1.6.1`, `--engine skill` (текущая папка навыка, включая незакоммиченные правки — отмечается в отчёте) или `--engine deck` (сборщик, лежащий в проекте).
3. **Сравнение:**
   ```bash
   $SKILL/.venv/bin/python -I $SKILL/scripts/version_compare.py compare version-runs/<прогон A> version-runs/<прогон B>
   ```
4. Отправь пользователю `report.md` и пары изменившихся слайдов (`pairs/<тема>_s<N>.png`) через `SendUserFile`. Если изменений нет, хватит строки отчёта.
5. Если слайды открывались в PowerPoint, повтори сравнение в новую папку (`--out`) с `--ppt-viewed "dark:3,5"` и `--ppt-notes "…"`. В отчёте появятся именно эти слайды этой темы. Не пиши «проверено в PowerPoint» про всю деку, если смотрели два слайда.

Входы берутся из проекта: `slides.js`, `data/`, `theme.json`, `deck.json`, `img/` и прочие файлы, кроме `out*`, `node_modules`, `user-edits`. Сборщик и компоненты (`build.js`, `lib.js`, `components.js`, `kit/`, `render.sh`, `bg.py`) — из `--engine`. Подложки берутся из `img/` проекта как есть. `--regen-bg` перерисует их `bg.py` из версии прогона, и тогда изменятся и сами подложки. Проекты, где сборщик дописан под деку (свои функции в `lib.js`), сравнивай с `--engine deck`: подмена сборщика тегом их сломает, и отчёт покажет это как ошибку сборки.

## Что лежит в папках

Ничего не перезаписывается. Папка прогона `<runs>/<время>_<метка>/` и папка сравнения создаются новыми, а существующая папка — ошибка.

| Прогон | Содержимое |
|---|---|
| `src/` | ровно те исходники, из которых собрано: входы проекта и подменённый сборщик |
| `pptx/<имя>_<тема>.pptx` | PPTX каждой темы |
| `png/<тема>/s<N>.png` | PNG каждого слайда, 1920×1080 |
| `manifest.json` | сборщик (тег, коммит, версия), среда, sha256 каждого входа по категориям, sha256 PPTX и его содержимого без даты создания, sha256 PNG, проверки, содержание слайдов (`content`) и его формат (`content_manifest`) |

| Сравнение | Содержимое |
|---|---|
| `pairs/<тема>_s<N>.png` | «A \| B» с подписью статуса, на каждый слайд каждой темы (12 слайдов × 2 темы = 24 пары) |
| `diff/<тема>_s<N>.png` | слайд B приглушённым серым, изменившиеся пиксели — пурпурным |
| `report.json` | машиночитаемый отчёт |
| `report.md` | отчёт для человека |

## Правки содержания отдельно от сборщика

Прогон сохраняет содержание каждого слайда из `out/slides.json`: компоненты, архетип, тексты и заметки (`manifest.json → content`).
Сравнение показывает по каждому слайду, что поменяли правкой: «компоненты: barsTrend → lineChart», «текст: убрано 1,
добавлено 2», «заметки изменены». В отчёте:
- колонка «Содержание (правка, не сборщик)» в таблице слайдов;
- строка «Слайды с правкой содержания: … Изменились без правки содержания: …». Различия первых — следствие правки, а не
  версии навыка;
- раздел «Компоненты по слайдам» (A и B, изменившиеся выделены);
- раздел «Изменения содержания (редакционные)» с убранными и добавленными строками.

### Когда содержание не сравнивается

Наличие и формат манифеста содержания проверяются отдельно от значений полей. Прогон пишет в `manifest.json → content`
только поля, которые сборщик действительно отдал в `out/slides.json`, а в `content_manifest` — формат (сейчас 1), список
полей и что не записано. Отсутствующее поле не превращается в пустое: сборщик 1.5.0 не пишет тексты, компоненты и заметки,
1.6.x не пишет заметки.

Содержание не сравнивается вовсе, если хотя бы у одной стороны:
- в манифесте нет содержания или `out/slides.json` не было;
- старый манифест: прогон записан до формата 1, и сборщик не отдал тексты (поля определяются по `src/out/slides.json`
  прогона, а без него — по содержанию: у всех слайдов пустые тексты);
- частичная структура: у слайда нет заявленного поля, поле не того типа, `content` не словарь слайдов;
- формат манифеста новее, чем умеет эта версия.

Тогда в отчёте раздел «Изменения содержания (редакционные)» говорит «Содержание не удалось сравнить» с причиной, колонка
содержания — «не сравнивалось», раздела «Компоненты по слайдам» нет, проверка `content` — «не выполнялась». Ничего не
помечается добавленным или удалённым. Если входы проекта совпадают по контрольным суммам, отчёт добавляет, что редакционных
правок не было. Вердикты по входам (`control`), пикселям (`pixels`), XML PPTX (`pptx-content`) и среде от этого не зависят.

Корректно пустой манифест формата 1 (пустые тексты, компоненты, заметки или ни одного слайда) сравнивается как обычно.
Если поле есть только с одной стороны (сравнение с 1.6.x: заметки), сравниваются общие поля, а отчёт пишет «Не сравнивались:
заметки (нет в A)». В `report.json → content_compare` лежат итог (`comparable`), причина, сравненные и пропущенные поля
и описание каждой стороны.

Регрессионный тест на синтетических прогонах: `zsh $SKILL/tests/version_compare/run.sh`.

Если в проекте есть `requirements.json`, прогон запускает и `brief_coverage.py check` (проверка `coverage`; карта берётся из
`out/coverage.json` проекта). Для сводного отчёта деки передай папку сравнения в `check_report.py --compare`
(`reference/17-check-report.md`).

## Как читать вывод

- **Контрольное сравнение версий навыка:** входы и значимая среда совпали, различаются только сборщик и компоненты. Изменившиеся слайды — результат новой версии. Это ещё не регрессия: посмотри пары и реши, намеренное ли изменение.
- **Контрольная повторная сборка:** совпадает всё, включая сборщик. Любое различие означает невоспроизводимую сборку, и её стоит разобрать.
- **Неконтрольное сравнение:** изменился бриф, разметка, тема, изображения, шрифт, Chrome, node, pptxgenjs или ОС. Отчёт перечисляет, что именно. Различия нельзя приписать версии навыка и нельзя называть регрессией навыка. Чтобы проверить версию, пересобери оба прогона на одинаковых входах в одной среде.
- Версии Python-библиотек и самих проверок (навык, из которого запущены `pptx_audit.py`, `facts_check.py`, `library_check.py`) записываются, но на картинку не влияют. Их изменение не делает сравнение неконтрольным, а отмечается как «влияет только на проверки».

Статусы слайдов: совпадает (попиксельно), изменился (число и доля пикселей, рамка изменений), нет в A, нет в B.

## Проверки и их статусы

У каждой проверки в отчёте есть статус, инструмент, область действия и замечания. «Пропущена» и «не выполнялась» не считаются пройденными.

| Проверка | Инструмент | Область |
|---|---|---|
| `build-<тема>` | `node build.js` версии прогона | вся дека |
| `render-<тема>`, `font-<тема>`, `overflow-<тема>` | `render.sh`, headless Chrome | все слайды, шрифт бренда, тексты за боксами |
| `audit-<тема>` | `pptx_audit.py` текущего навыка | PPTX целиком |
| `facts`, `library` | `facts_check.py`, `library_check.py` текущего навыка | числа деки, тела слайдов; сборщик до 1.6.0 не помечает компоненты, у него `library` не проходит по определению |
| `bg` | `bg.py` | пропущена без `--regen-bg` |
| `pixels` | Pillow | все пары |
| `control` | контрольные суммы и среда | пройдена, только если сравнение контрольное |
| `pptx-content` | sha256 XML внутри PPTX без `docProps/core.xml` | различие XML при совпавших PNG — повод открыть PowerPoint |
| `content` | манифест содержания обоих прогонов | «не выполнялась», если содержание не удалось сравнить (причина в замечаниях) |
| `powerpoint` | просмотр человеком или агентом | по умолчанию «не выполнялась»; с `--ppt-viewed` — только перечисленные слайды |

## Ограничения (переносятся в каждый отчёт)

PNG рендерятся из HTML-двойника в headless Chrome. Попиксельное совпадение не подтверждает, что PPTX так же выглядит
в PowerPoint (шрифты, переносы, автоподбор), и не оценивает качество дизайна: одинаково плохой слайд совпадёт сам с собой.
Шрифты определяются по `fc-list` или файлам в `~/Library/Fonts` и `/Library/Fonts`. Если начертание не найдено, в манифесте
у семейства пустой список, а проверка `font-<тема>` показывает, загрузился ли шрифт при рендере.
